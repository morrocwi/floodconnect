# โครงสร้าง topology ของ FloodConnect (build 3, 2026-09-27)

**คำสั่งฟาวน์เดอร์ (17:08, คำต่อคำ)**: "เอาเลย สร้าง floodconnect topology จากสิ่งที่เรามี"

เอกสารนี้เป็น `MEASURED` (อ่านจากกราฟที่ build จริงในเครื่อง, `output/thailand_water_kg.graphml`
build 3) + `RELAYED` เฉพาะจุดที่อ้างอิงเอกสารอื่น (มีระบุชัดเจนเป็นราย ๆ) — ไม่มีการเดา/geocode
ใด ๆ เพิ่มเติมจากที่มีอยู่แล้วในคลังนี้

---

## ภาพรวม: 5 ชั้น จากแม่น้ำ → คลอง → ท่อระบายน้ำ → เขต → สินทรัพย์

```
river_reach (HydroRIVERS, RELAYED)
    │ WATER
canal / canal_node (Wikipedia + OSM + east_chain, RELAYED/OPEN)
    │ WATER, DRAINS_TO (junction→canal, ใหม่ build 3)
drain_junction (ชื่อถนน/ทางแยก/คลองจาก PIPE_FROM/PIPE_TO, ใหม่ build 3)
    │ DRAINS_TO
drain_segment (1 แถวต่อ 1 ด้าน R/L/ROAD/PJ จาก CSV กทม., ใหม่ build 3)
    │ IN_DISTRICT (ใหม่ build 3)
district (50 เขต, geo node ใหม่ build 3) ── แยกจาก AG_DIST_SS (governance office เดิม)
    │
asset (ประตู/สถานีสูบ/มาตรวัด ฯลฯ — มีอยู่แล้วตั้งแต่ build 1/2)
```

**สิ่งที่ยังไม่ทำ (ตามกฎ)**: ไม่มีการ geocode ชื่อถนน/ทางแยกใน `PIPE_FROM`/`PIPE_TO` เทียบกับ
gazetteer ใด ๆ — ทุก edge ในชั้นนี้เป็น edge ตามชื่อที่ตรงกัน (explicit) เท่านั้น ไม่ใช่ตามระยะทาง

## ชั้น 1: ท่อระบายน้ำ กทม. (drain_segment / drain_junction) — ใหม่ build 3

**แหล่งข้อมูล**: `data.bangkok.go.th/dataset/drain-pipe` (สำนักการระบายน้ำ กทม.) — CSV 2,903
แถว, เก็บที่ `raw/live/bma_open_data_drainage_org/drain_pipe_full.csv` (encoding: cp874/
TIS-620, ยืนยันถอดรหัสได้สะอาดทั้งไฟล์), parse โดย `tools/harvest/bma_drain_pipes.py` →
`sources/bma_drain_pipes.yaml`

- **1 แถว CSV อาจมี 1-4 ด้านท่อ** (R=ขวา, L=ซ้าย, ROAD=รางระดับถนน, PJ=ท่อดันลอด) แต่ละด้านมี
  ขนาด/ความยาว/ประเภทของตัวเอง → parser สร้าง **3,406 `drain_segment` node** (หนึ่งต่อหนึ่ง
  (แถว, ด้าน) ที่มีข้อมูลจริง — แถวที่ทุกด้านว่างเปล่าถูกข้าม ไม่สร้าง node ปลอม)
- **2,915 จาก 3,406 รายการมีทั้ง `PIPE_FROM` และ `PIPE_TO`** (ใช้ topology ได้จริง) ส่วนที่เหลือ
  มีด้านใดด้านหนึ่งว่างหรือทั้งคู่ว่าง — เชื่อมได้บางส่วนหรือเชื่อมไม่ได้เลย (แต่ node ยังถูกเก็บไว้
  พร้อม attribute ครบ ไม่ทิ้งข้อมูล)
- **`drain_junction`: 1,077 node** — หนึ่ง node ต่อหนึ่งชื่อ `PIPE_FROM`/`PIPE_TO` ที่ต่างกัน
  (ชื่อถนน/ทางแยก/ชื่อคลอง ตามที่ไฟล์ต้นทางระบุ ไม่ใช่พิกัด)
- **`DRAINS_TO` edge**: `segment → junction(PIPE_TO)` และ `junction(PIPE_FROM) → segment`
  เฉพาะกรณีฟิลด์นั้นไม่ว่างเท่านั้น — 5,885+1,264 = **7,149 edge รวม** (ดูรายละเอียด tag
  แยกใน `tools/kg/README.md`)
- **`junction → canal` (คลองที่มีอยู่แล้วในกราฟ)**: จับคู่ชื่อ junction (หลัง
  `normalize_canal_name()` — ตัดคำ "คลอง" นำหน้า + ตัดช่องว่างส่วนเกิน) กับดัชนีชื่อคลอง
  รวม (canal/canal_node จาก Wikipedia+east_chain + ชื่อ edge ของ OSM) — **1,264 edge จับคู่ได้**
  จาก 1,077 junction (junction เดียวจับคู่ได้มากกว่า 1 edge ได้ ถ้าชื่อเดียวกันปรากฏทั้งฝั่ง
  PIPE_FROM และ PIPE_TO ของแถวต่าง ๆ)
- **413 → 513 connected component**: กราฟท่อกระจัดกระจายมาก (4,483 node ท่อ+junction แบ่งเป็น
  513 กลุ่มที่แยกจากกัน) — สะท้อนว่าข้อมูล topology จริงในไฟล์ CSV **ไม่ครบ** (หลายแถวไม่มี
  `PIPE_FROM`/`PIPE_TO` เลย) ไม่ใช่ข้อผิดพลาดของการ join ในงานนี้

### ชุดข้อมูลเสริม: บ่อสูบน้ำ pipe-jacking (มีพิกัดจริง)

`data-pipe-jacking.csv` (ชุดข้อมูลพี่น้อง, ไม่ใช่ท่อ topology แต่เป็น**บ่อสูบน้ำ**ที่เกี่ยวข้องกับ
งานท่อดันลอด) — 13 แถว, มีพิกัด **UTM Zone 47N (EPSG:32647) จริง** ในไฟล์ต้นทางเอง แปลงเป็น
WGS84 ด้วย pyproj (การแปลงระบบพิกัด ไม่ใช่การเดา/geocode) เก็บใน `sources/bma_drain_pipes.yaml`
`sump_wells` — **ยังไม่ได้ผูกเข้ากราฟเป็น node** (เสนอไว้ใน "ขั้นถัดไป" ด้านล่าง)

## ชั้น 2: คลอง (canal / canal_node) — ปรับปรุงจาก build ก่อนหน้า

**Wikipedia canals WATER-edge resolution ดีขึ้นจาก 7/175 → 72/175 ในงานนี้** โดยเพิ่มการจับคู่
แบบ normalised name (ตัดคำ "คลอง" นำหน้า) เทียบกับ:
- ดัชนีชื่อ edge ของ OSM canal graph (`output/bangkok_canals.graphml`, 939 ชื่อที่ต่างกัน)
- ป้ายชื่อ 18 node ของ site canal_graph (`site/inputs/canals/east_chain.yaml`)

**ยังเหลือ 103/175 ชื่อ upstream/downstream ที่จับคู่ไม่ได้** — ส่วนใหญ่เป็นชื่อภูเขา/จังหวัด/
ปากแม่น้ำที่ไม่มี node ใด ๆ ในกราฟนี้เลย หรือเป็นการสะกดที่ต่างกันซึ่งกฎ "ตรงกันเป๊ะหลัง
normalise เท่านั้น ห้ามเดา" ของโปรเจกต์นี้ปฏิเสธไม่จับคู่ให้อย่างถูกต้อง

**Site canal_graph (18 node ที่ maintainer ประกาศเอง, `east_chain.yaml`)** ถูกนำเข้ากราฟแล้ว
ตั้งแต่ build ก่อนหน้า (ผ่าน `load_east_chain()`) — งานนี้ไม่ต้องเพิ่มซ้ำ เพียงยืนยันว่ายังอยู่ใน
กราฟและใช้ป้ายชื่อของมันเป็นส่วนหนึ่งของดัชนีจับคู่คลองด้วย

## ชั้น 3: เขต (district) — geo node ใหม่ แยกจาก governance office

**แหล่งข้อมูล**: `sources/bkk_district_elevation.yaml` (สุ่มอ่านระดับความสูง 1 จุดต่อเขต จาก
แผนที่ RTSD ต.ค. 2553 ที่ georeference ไว้แล้วในคลังนี้) — **50 `district` node** (หนึ่งต่อหนึ่ง
เขต กทม.)

**สำคัญ: แยกจาก `AG_DIST_SS` (governance-DAG node เดิม)** — `AG_DIST_SS` คือ**สำนักงานเขต
สะพานสูง** (อำนาจสั่งการ/CMD edges เช่น สั่งอพยพ) ส่วน `district:1044` (node ใหม่) คือ**พื้นที่
ภูมิศาสตร์เขตสะพานสูง** (ระดับความสูง/below-MSL) — สองมิติคนละเรื่องกัน ผสมกันจะทำให้ query
อำนาจ (bottleneck analysis ใน `tools/dag/bottlenecks.py`) กับ query ความเสี่ยงภูมิศาสตร์ปนกัน
โดยไม่จำเป็น (ข้อเสนอนี้มาจาก `docs/knowledge/BKK_DISTRICT_ELEVATION.md` เอง, งานนี้แค่ implement)

- **25/50 เขต มีค่าระดับความสูงที่อ่านได้มั่นใจ** (tag `VERIFIED-from-map` ในไฟล์ต้นทาง, พับเป็น
  `OPEN` ในระดับ node tag ของกราฟเพราะ `VERIFIED-from-map` ไม่ใช่ tag ที่กราฟนี้รู้จัก — ดู
  `tools/kg/README.md`)
- **25/50 เขต ยังเป็น OPEN** (จุดสุ่มปนเปื้อนจากตัวอักษร/เส้นแผนที่ — ดู
  `docs/knowledge/BKK_DISTRICT_ELEVATION.md` เอง)
- **`IN_DISTRICT` edge**: 3,275 edge รวม — 3,179 จาก `drain_segment` (ตามฟิลด์
  `DISTRICT_NAME` ของ CSV กทม.เอง) + 96 จาก asset ที่มี `notes` field แบบ
  `"district: <name>"` (harvest เดิมของ `assets_registry.py`, รูปแบบเดียวกับ `basin:` ที่ใช้
  สร้าง `IN_BASIN` อยู่แล้ว)
- **3 ชื่อเขตจับคู่ไม่ได้** (สะกดต่างกันระหว่างสองแหล่ง): `บางชื่อ`/`ป้อมปราบฯ`/`ราษฎร์บูรณะ`
  (จาก asset notes) เทียบกับ `บางซื่อ`/`ป้อมปราบศัตรูพ่าย`/`ราษฏร์บูรณะ` (จาก
  `bkk_district_elevation.yaml`) — สังเกตคู่สุดท้าย: `ฎ` vs `ฏ` เป็นตัวสะกดที่ต่างกันจริง ไม่ใช่
  error การอ่าน — ไม่ได้ fuzzy-match ตามกฎของโปรเจกต์นี้

## นักบิน Sammakorn (เขตสะพานสูง): สิ่งที่พบจริง

**เขตสะพานสูงมีแถวใน CSV ท่อระบายน้ำ กทม. น้อยที่สุดในบรรดา 50 เขต — เพียง 4 รายการ**
(เทียบ พระนคร 281, บางกะปิ 278, ดุสิต 216 — ค่ามัธยฐานของเขตอื่นอยู่ที่หลักสิบถึงหลักร้อย)
สอดคล้องกับ `docs/knowledge/DRAINAGE_NETWORK_SOURCES.md`'s finding ว่าความครอบคลุมของ CSV
นี้ **ไม่สม่ำเสมอ** ข้ามเขต — ไม่ใช่แค่ Sammakorn ที่ข้อมูลน้อย แต่สะพานสูงน้อยที่สุดในทุกเขต

รายละเอียด 4 แถว (ทั้งหมด `VERIFIED-from-official-csv`, ไม่มีพิกัด):

| pipe_from | pipe_to | ผลจับคู่คลอง |
|---|---|---|
| ถนนรามคำแหง | ถนนวงแหวนกาญจนา | ไม่จับคู่ (ชื่อถนน ไม่ใช่คลอง) |
| ถนนรามคำแหง | ถนนวงแหวนกาญจนา | (แถวซ้ำ, คนละด้าน R/L) |
| กรุงเทพกรีฑาซอย 9 | **คลองวังใหญ่** | **จับคู่ได้** → `osmcanal:100.68000,13.75470` (OSM node ที่มี edge ชื่อ "คลองวังใหญ่") |
| กรุงเทพกรีฑาซอย 9 | **คลองวังใหญ่** | (แถวซ้ำ, คนละด้าน R/L) |

**ผลสรุป**: ท่อระบายน้ำ 2 จาก 4 รายการที่ กทม. รายงานไว้ในเขตสะพานสูงเชื่อมเข้า**คลองวังใหญ่**
ได้จริง (ตรงกับ `wangyai` node ใน `site/inputs/canals/east_chain.yaml` โดยชื่อ — แม้ยังไม่ได้
ผูก edge ตรงระหว่าง `drainjunction` กับ `canalchain:wangyai` เพราะ `east_chain.yaml`'s ชื่อ
label คือ `"คลองวังใหญ่บน"` ไม่ใช่ `"คลองวังใหญ่"` เป๊ะ — ต่างกันแค่คำว่า "บน" ท้ายชื่อ ซึ่งกฎ
"ตรงกันเป๊ะหลัง normalise เท่านั้น" ของโปรเจกต์นี้ไม่จับคู่ให้ ถูกต้องตามกฎ แต่เป็นช่องว่างที่
ควรตรวจสอบด้วยมนุษย์ว่าเป็นคลองเดียวกันจริงหรือไม่ — ไม่จับคู่ทับซ้อนกันเอง). **ไม่พบแถวใดใน
CSV นี้ที่อ้างถึง "คลองบ้านม้า" ในเขตสะพานสูงเลย** — คลองบ้านม้าที่พบใน CSV (3 junction:
`คลองบึงบ้านม้า`, `คลองบ้านม้า 1`, `คลองบ้านม้า 2`) ทั้งหมดอยู่ในเขต**สวนหลวง**และ**บางกะปิ**
ไม่ใช่สะพานสูง — คลองบ้านม้าที่ maintainer ประกาศไว้ใน `east_chain.yaml` (`banma` node) จึง
**ยังไม่มีหลักฐานจาก CSV ท่อระบายน้ำของ กทม. ที่เชื่อมโยงกับเขตสะพานสูงโดยตรง** (สอดคล้องกับ
`east_chain.yaml`'s ของมันเองที่บอกว่า `banma` "ไม่มีเครื่องวัด...ไม่พบในรายการสถานีใดของ กทม."
— ตอนนี้ยืนยันเพิ่มเติมว่าไม่พบใน CSV ท่อระบายน้ำเช่นกัน)

**สรุปหนึ่งบรรทัดสำหรับ Sammakorn**: ท่อระบายน้ำสาธารณะที่ กทม. รายงานในเขตสะพานสูงมีน้อยมาก
(4 แถว) — 2 แถวเชื่อมคลองวังใหญ่ได้ (ชื่อใกล้เคียง `wangyai` node ที่มีอยู่แล้ว แต่ยังไม่ผูก
edge ตรงเพราะชื่อไม่ตรงเป๊ะ), ไม่มีแถวใดเชื่อมคลองบ้านม้า, และ**ระบบท่อระบายน้ำภายในหมู่บ้าน
สัมมากรเองไม่มีในแหล่งสาธารณะใด ๆ ที่สำรวจมา** (ยืนยันซ้ำจาก
`docs/knowledge/DRAINAGE_NETWORK_SOURCES.md`) — ต้องขอจากนิติบุคคลหมู่บ้านโดยตรงเท่านั้น

## แหล่งข้อมูลถัดไปที่ต้องการ

- **การ geocode ชื่อถนนใน `PIPE_FROM`/`PIPE_TO`** เทียบ OSM road gazetteer — จะทำให้
  `drain_segment`/`drain_junction` มีพิกัดได้ แต่เป็นขั้นตอน **inference ใหม่** ต้องติด
  `INSTINCT` tag + ฟาวน์เดอร์อนุมัติก่อนตามกฎของโปรเจกต์นี้ — **ยังไม่ทำในงานนี้**
- **BMA GIS `water_manag_data` folder** (token-gated, ArcGIS) — พบว่าเป็นที่ตั้งของ GIS
