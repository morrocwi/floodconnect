**เขียน**: 2026-09-27 · โดย `tools/layer0/` (ไม่ได้ผูกเข้ากับ `site/build_data.py`/`build_page.py` ในงานนี้
— อีก worker เป็นผู้ commit และตัดสินใจว่าจะเรียกใช้ฟังก์ชันเหล่านี้จากไปป์ไลน์จริงอย่างไร)

**ต้นเหตุ (คำพูดผู้ก่อตั้ง 2026-09-27)**: "จริงๆ การพยากรณ์เบื้องต้นไม่ซับซ้อน ... กทม. มีความสามารถ
รับฝนที่ xxx แต่วันนี้ฝนจะตกในพื้นที่ xxx+1 หรือกำลังมีน้ำที่มาจากต้นทางที่ xxx+1 ในกี่ชั่วโมง ... แล้วค่อยไป
ลงรายละเอียด" → "เอาแบบง่ายๆ ก่อน น้ำเข้า น้ำออก ความสามารถในการรับมือ"

## 1. กติกา

ต่อหนึ่งหน่วย (unit) มีตัวเลข 3 ตัว, **แต่ละตัวมีแหล่ง+แท็ก+เวลา**, และหนึ่งประโยครวม:

- **น้ำเข้า (IN)**: ฝนพยากรณ์ 24 ชม. ข้างหน้า (ensemble median+max, RELAYED) + ฝนวัดจริง 24 ชม.
  ที่ผ่านมา (MEASURED) + น้ำต้นทางที่จะมาถึงภายใน τ ชม. (river: C.13/C.2 เทียบ τ; BKK east: 0
  เว้นแต่มีประตูเปิดที่ ΔH>0) + **น้ำย้อนจากคลอง** (สำหรับหน่วยที่เชื่อมคลอง เช่น สัมมากร — ดู §2)
  — หน่วยเดียวกับ CAPACITY เสมอ, ระบุการแปลงหน่วยชัดเจน
- **น้ำออก (OUT)**: กำลังสูบที่วิ่งอยู่จริงตอนนี้ + ช่องว่างทางออกแรงโน้มถ่วง (ความจุช่วง − อัตราปัจจุบัน)
- **รับมือได้ (CAPACITY)**: ทั้งค่าออกแบบ (design, ถ้ามี) **และ** ค่าประวัติศาสตร์ที่เคยท่วม/เคยรับได้
  (ดู §4 — coping_thresholds.yaml)
- **READOUT**: "IN vs CAPACITY → เกิน/ไม่เกิน/ใกล้(≥80%)" และ "OUT vs IN → ระบายทัน/ไม่ทัน/ไม่รู้"
  + เวลาที่จะเกิน (ถ้า IN เป็นอัตรา) — ตัวเลขที่ขาดแหล่งจะ **REFUSED** เฉพาะตัวนั้น ไม่ทำให้ทั้งประโยค
  หายไป ("ขาด: OUT" ยังต้อง render ได้)

**ไม่มีสมการใหม่** — โมดูลนี้เป็น PROPOSAL-derived simplification ของ `PROP-FLOOD-06` (ดู §3).

## 2. น้ำย้อนจากคลอง (canal backflow)

**คำแก้ไขผู้ก่อตั้ง (คำพูดตรง)**: "สัมมากรต้องเชื่อมกับน้ำในคลองด้วย เพราะมันเป็นน้ำย้อนจากคลอง ไม่ใช่
แค่ปั๊ม" — สำหรับหน่วยที่เชื่อมคลัง (สัมมากรและหน่วยใดก็ตามที่ต่อคลอง) น้ำเข้ามี 3 ส่วน: ฝน +
น้ำต้นทาง + **น้ำย้อนจากคลอง**.

`compute_backflow_state()` (`tools/layer0/in_out_capacity.py`) คืนสถานะ `{active | not_active |
unknown | likely}` ไม่ใช่ตัวเลข m³/s ที่กุขึ้นมาเอง:

1. **หลักฐานชุมชนตรง** (community eyewitness) — เช่น รายงาน 26 ก.ย. 2569 ซอย 59 "จากท่อน้ำคลอง"
   06:00-10:00, ซอย 17 "ย้อนขึ้นท่อ" 11:10 (`site/inputs/community/community_reports_2026-09-26.md`)
   → `active`, tag `MEASURED-community`
2. **ระดับคลอง/บึงบน datum เดียวกัน** → head = คลอง − บึง (ม.); head>0 และจุดต่อไม่ปิด → `active`
3. **คนละ datum, เทียบ band** — คลองสูงกว่า critical ของตัวเอง **และ** บึงต่ำกว่า bank ของตัวเอง →
   `likely`, tag `INSTINCT` (ไม่แปลงเป็นตัวเลข m³/s)
4. ไม่มีหลักฐานใดเลย → `unknown`

**สัมมากรวันนี้ (26-27 ก.ย. 2569)**: canal_backflow = **active** (MEASURED-community, จากซอย
59/17) — WL.BMA.02 (คลองบ้านม้า, รามคำแหง) อ่านได้ 0.73 ม. (warning=2.14 ดูเหมือนไม่ตรงกับค่าจริง,
OPEN), water_control (ระดับปกติที่ประกาศ) เป็น `null` ทุกสถานี — ไม่มีค่าระดับ "ปกติ" ที่ยืนยันได้
(`docs/knowledge/BMA_WATER_MAP_PROBE.md`), จึงยังไม่มี head ที่คำนวณจาก datum เดียวกัน — ใช้ case 1
(หลักฐานชุมชน) เป็นหลัก.

## 3. แมปกับ PROP-FLOOD-06 (Toledo — ไม่ใช่สมการใหม่)

| Layer 0 | PROP-FLOOD-06 (`toledo-wt-flood06/docs/proposals/PROP-FLOOD-06.md`) |
|---|---|
| IN | `F_H(U)` — inflow term (ฝน + upstream, ขยายเป็น leading inputs ใน v5) |

| time_to_exceed | อ้างไอเดียของ `PROP-FLOOD-02` (`T_k := (theta-h(t))·k/Delta_k(t)`) — **ไม่ใช่การ implement
  PROP-FLOOD-02 ให้ live** (`AGENTS.md` §8 บันทึกว่า PROP-FLOOD-02 ยังไม่ implement ที่ไหนเลย — ยังจริงอยู่
  หลังไฟล์นี้, เพราะ `time_to_exceed_hours()` คำนวณตรงในโมดูลนี้ ไม่ได้เรียก PROP-FLOOD-02) |

**Layer 1 เปิดเมื่อไหร่**: เฉพาะเมื่อ Layer 0 บอก "เกิน"/"ใกล้" หรือ "น้ำยังค้างอยู่" (ปั๊ม/ประตู/ΔH/
typology ตาม PROP-FLOOD-06's fuller tier) — ไม่เปิดทุกครั้ง ตามคำสั่งผู้ก่อตั้ง "แล้วค่อยไปลงรายละเอียด".

## 4. coping_thresholds.yaml — ค่ารับมือจากประวัติศาสตร์

**คำสั่งผู้ก่อตั้ง (คำพูดตรง)**: "ซึ่งค่ารับมือพวกนี้อ่านจากประวัติได้ เรามีประวัติศาสตร์และงานวิจัยเยอะ"

`sources/coping_thresholds.yaml` รวมทุกค่า "ท่วมที่ X" / "รับได้ถึง X" ที่มีอยู่แล้วในคลัง
(case_*.md, card_research_*.md, capacity_ledger(+additions).yaml, DATA_SWEEP_2026-09-27.md,
docs/CAPACITY.md, raw/backtest/events.yaml, community_reports_2026-09-26.md) เป็นแถวเดียว
ต่อ unit×variable แล้วอนุมาน:

- `threshold_flooded_min` := ค่าน้อยสุดที่เคยท่วม
- `threshold_coped_max` := ค่ามากสุดที่เคยรับได้ (ไม่ท่วม) — **ไม่ใช่ design figure** (ค่าออกแบบเก็บแยก
  เป็น `design`)
- `gap` := ช่วงที่ไม่รู้ (flooded_min − coped_max) — เป็นความไม่รู้ที่ซื่อสัตย์ ไม่ใช่คะแนนความเสี่ยง
- `one_sided: true` เมื่อมีข้อมูลด้านเดียว

## 5. บันไดฝน กทม. จากหลักฐาน (Bangkok rain ladder)

**คำถามผู้ก่อตั้ง (คำพูดตรง)**: "หาด้วยว่าจริงๆ แล้วในอดีต กทม. รับฝนได้แค่ไหนโดยไม่ท่วม และเท่าไหร่คือ
อันตราย และเท่าไหร่คือวิกฤต และเท่าไหร่คือมหาอุทกภัย"

**เป็นตารางหลักฐาน ไม่ใช่คำตัดสิน** — ทุกแถวติดแท็ก, ไม่มีตัวเลขเดียวที่เป็น "the" threshold:

| ออกแบบ (JICA เป้า/ปัจจุบันอ้างถึง) | 76-100 mm/h | ทั้งเมือง | design_only, ขัดกับแถวบน (OPEN) | ข่าวแผนแม่บท JICA | RELAYED |

| **danger_min** (ท่วมขังถนน) | OPEN | — | ไม่พบตัวเลขที่แยกจาก crisis ข้างล่าง | — | OPEN |

พร้อมตัวเลขและผล มีเพียงจุดเดียวที่ยืนยันได้แน่ (`crisis_min` = 203.0 mm/24h) และ 2554 เป็นคนละแกน
(ปริมาณน้ำต้นทาง+ระยะเวลา ไม่ใช่ฝนรายวันของ กทม. เอง). ช่องว่างระหว่าง design (58.7mm/h≈80mm/day)
กับ crisis_min (203mm/24h) เป็น**ช่วงไม่รู้ที่ใหญ่ที่สุด** ของบันไดนี้.
