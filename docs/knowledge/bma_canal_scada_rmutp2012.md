## (b) โครงสร้างระบบ

### ศูนย์ควบคุมระบบป้องกันน้ำท่วมกรุงเทพมหานคร (RELAYED, หน้า 171)
- ที่ตั้ง: อาคารสำนักการระบายน้ำ ชั้น 6 ศาลาว่าการ กทม. 2 เขตดินแดง
- เปิดใช้งานปี พ.ศ. 2533 แล้วขยายพื้นที่ควบคุมให้ครอบคลุมทั้ง กทม.
- ใช้เทคโนโลยี SCADA (Supervisory Control and Data Acquisition) ควบคุมสถานีสูบน้ำแต่ละตำแหน่งทั่ว กทม.
- โครงสร้างแบ่งเป็น "สถานีแม่ข่าย" (master, 1 สถานี ตั้งอยู่ที่ศูนย์ควบคุมฯ) และ "สถานีเครือข่าย" (field/slave stations)
- ค่าที่สถานีเครือข่ายวัด: ระดับน้ำในคลอง, ปริมาณฝน, ระดับการเปิด-ปิดประตูระบายน้ำ, สถานการณ์ทำงานของเครื่องสูบน้ำ
- ระบบแบ่งออกเป็น 2 ระบบย่อยคู่ขนาน: **ระบบโทรมาตร** (Field Server) และ **ระบบตรวจวัดระดับน้ำในคลองหลัก** (Canal Regulation)

### 1. ระบบโทรมาตร (Field Server) — หน้า 171–173
- ใช้ SCADA + ช่องทางสื่อสารคลื่นวิทยุ (Radio) ย่าน **UHF 446.25 MHz** ระหว่างสถานีแม่ข่ายกับสถานีสนาม
- ซอฟต์แวร์ควบคุม: **Wizcon** — เรียกข้อมูล (Polling) ไปยังสถานีเครือข่ายทุก **15 นาที** ไล่จากสถานีที่ 1 ถึงสถานีที่ 75
- จำนวนสถานีเครือข่าย: **75 สถานี** ทั่วพื้นที่ กทม. (RTU: Remote Terminal Unit ที่แต่ละสถานีสนาม)
- Sensor อินพุต 5 ชนิดตามที่ออกแบบไว้: (1) เครื่องวัดปริมาณฝน (2) เครื่องวัดระดับน้ำ (3) สถานะเครื่องสูบน้ำ
  (4) เครื่องวัดระดับเปิด-ปิดประตูน้ำ (5) เครื่องวัดคุณภาพน้ำ — **แต่บทความระบุว่า ณ ตอนเขียน (2012)
  เครื่องวัดคุณภาพน้ำถูกยกเลิกออกจากระบบแล้ว** เหลือใช้งานจริง 4 ชนิด
- เส้นทางข้อมูล: Sensor → RTU (ประมวลผลที่สถานีสนาม, มี CPU + Input Module รับ Analog 4-20mA และ Digital On/Off)
  → Gateway → SCADA Server → Database Server ที่ศูนย์ควบคุมฯ (แสดงผลแบบฐานข้อมูล + กราฟิก GUI)
- เวลาที่ใช้: เรียกข้อมูล 1 สถานีใช้เวลาประมาณ 6 วินาที; เรียกครบ 75 สถานี 1 รอบใช้เวลาประมาณ 7 นาที

### 2. ระบบตรวจวัดระดับน้ำในคลองหลัก (Canal Regulation) — หน้า 173–175
- เป็นระบบตรวจวัดระดับน้ำแบบส่งสัญญาณอัตโนมัติ แสดงผลที่ศูนย์ควบคุมฯ
- จำนวนสถานีตรวจวัด: **40 จุด** (ติดตั้งบริเวณริมคลองพื้นที่ต่ำเสี่ยงน้ำท่วมขัง เช่น คลองบางจาก เขตภาษีเจริญ — สถานีตัวอย่าง BJ01)
- การสื่อสาร: Client (สถานีตรวจวัด) ↔ Server (ศูนย์ควบคุม) ผ่าน Protocol **Modbus TCP/IP**;
  ข้อมูลจากอุปกรณ์วัดเป็น Modbus RTU ก่อน แล้วแปลงเป็น Modbus TCP/IP ผ่าน **GPRS Modem**
- Polling ทุก **15 นาที** (ผู้ใช้กำหนดช่วงเวลาได้ — Defined Polling)
- ส่วนประกอบหลัก: (1) เครื่องวัดระดับน้ำ ทำหน้าที่ Controller ส่ง Output ผ่านพอร์ต RS232
  (2) Modem ส่งข้อมูลผ่าน GPRS ไปยังศูนย์ควบคุมฯ
- เรียกข้อมูลครบ 40 สถานีใน 1 รอบใช้เวลาประมาณ **30 วินาที**
- ใช้บริการ GPRS ของ AIS (มีหลาย Cell Site ครอบคลุมพื้นที่ตรวจวัด — สลับ Cell Site อัตโนมัติเมื่อสัญญาณมีปัญหา)

### เครื่องมือวัดระดับน้ำ (หน้า 175–176)
- ชนิดที่ใช้: **Float Type** (เครื่องวัดแบบลูกลอย) — Pulley (จานหมุน) + Counterweight (เครื่องถ่วง) +
  Floats (ลูกลอย) + beaded float line (สายสลิง)
- Pulley เส้นผ่านศูนย์กลาง 16.5 ซม. หมุน 1 รอบ = ระดับน้ำเปลี่ยน 50 ซม.
- ระยะวัด: 0–65.535 เมตร (ตามมาตรฐาน)
- ความถูกต้อง: คลาดเคลื่อนไม่เกิน ±1 มิลลิเมตร (ตามที่บทความระบุ)
- ความละเอียด: ถึงหน่วยมิลลิเมตร; ความเร็วในการวัดสูงสุด 2 รอบ/วินาที

## (c) ตัวเลขภาพรวมคลอง กทม. (หน้า 170, RELAYED 2012)

- คลองในกรุงเทพมหานครทั้งหมด: **1,161 คลอง** ความยาวรวม **2,272 กิโลเมตร**
- คู/ลำราง/ลำกระโดง: 521 แห่ง ความยาวรวม 321 กิโลเมตร
- ในความรับผิดชอบของ**สำนักการระบายน้ำ (สนน.)**: คลอง **213 คลอง** ความยาว **952 กิโลเมตร**;
  คู/ลำราง/ลำกระโดง 5 แห่ง ความยาวรวม 7 กิโลเมตร
- ส่วนที่เหลือ (คลองที่ไม่ใช่ 213 คลองข้างต้น) อยู่ในความรับผิดชอบของ**สำนักงานเขตต่าง ๆ**
- พื้นที่ลุ่มน้ำเจ้าพระยาโดยรวม (บริบท, หน้า 170): ~160,000 ตร.กม. (~1/3 ของพื้นที่ประเทศไทย)
- ระดับพื้นดินเฉลี่ยของ กทม.: สูงกว่าระดับน้ำทะเลปานกลางประมาณ 1–1.5 เมตร

## (d) ข้อดี/ข้อจำกัดที่บทความวิเคราะห์ (verbatim-faithful, หน้า 176–178)

### 2.1 ระบบโทรมาตร
**ข้อดี**
- สามารถแสดงผลข้อมูลได้หลายพารามิเตอร์ (ระดับน้ำ, ฝน, สถานะประตู, สถานะเครื่องสูบ)
- ใช้บริการ GPRS ของ AIS ซึ่งมีหลาย Cell Site ครอบคลุมพื้นที่ตรวจวัด
- เรียกข้อมูลครบทั้งหมด 40 สถานี (*หมายเหตุ: ข้อความต้นฉบับปะปนตัวเลขของทั้งสองระบบในย่อหน้าเปรียบเทียบ —
  ดูหมายเหตุด้านล่าง*) ใน 1 รอบใช้เวลาประมาณ 30 วินาที
- GPRS เสถียรกว่าวิทยุ → ข้อมูลขาดหายน้อยกว่า

**ข้อจำกัด**
- แสดงข้อมูลได้เพียง 1 พารามิเตอร์ต่อจุด (ระดับน้ำ) — ในบางย่อหน้า / เอกสารต้นฉบับมีความคลุมเครือ
  ระหว่าง "ระบบโทรมาตร" กับ "ระบบตรวจวัดระดับน้ำในคลองหลัก" ว่าใครแสดงกี่พารามิเตอร์ — ทำเครื่องหมาย OPEN
- หากระบบ GPRS ของผู้ให้บริการล่ม จะไม่สามารถส่งข้อมูลได้
- มีค่าบริการรายเดือน 150 บาท/เดือน/จุด
- ไม่สามารถเพิ่มเซ็นเซอร์อินพุตได้
- ต้องใช้พื้นที่ติดตั้งตู้ RTU + เสาอากาศสูง 15 เมตร
- ใช้งบประมาณก่อสร้างสูง
- ต้องเขียนคำสั่งควบคุม RTU เอง
- มีส่วนประกอบมากและอุปกรณ์ราคาแพง
- ไม่สามารถส่งข้อมูลได้หากสัญญาณวิทยุขัดข้อง
- สัญญาณวิทยุถูกลดทอนง่ายจากสภาพภูมิประเทศ/อากาศที่เปลี่ยนแปลง (โดยเฉพาะพื้นที่ตึกสูงใน กทม.)
- การเรียกข้อมูล 1 สถานีใช้เวลาประมาณ 6 วินาที; ครบ 75 สถานีใน 1 รอบ ใช้เวลาประมาณ 7 นาที

### 2.2 ระบบตรวจวัดระดับน้ำในคลองหลัก
**ข้อดี**
- ใช้พื้นที่ติดตั้งน้อย
- ใช้งบประมาณก่อสร้างไม่สูง
- ระบบไม่ยุ่งยากซับซ้อน
- เมื่อสัญญาณ GPRS มีปัญหากับ Cell Site หนึ่ง จะสวิตช์ไปเชื่อมต่อ Cell Site อื่นทันที
  → การติดต่อต่อเนื่อง ข้อมูลขาดหายน้อยกว่าระบบโทรมาตร, ความเร็วส่งข้อมูลสูงกว่ามาก
- ต่อเซ็นเซอร์เพิ่มได้ (ข้อได้เปรียบเมื่อคลองใหญ่/ปากคลองต้องเก็บสถานะประตูน้ำเพิ่มเติม)

**ข้อจำกัด**
- มีค่าบริการ GPRS รายเดือนต่อเนื่อง → งบประมาณสูงกว่าในระยะยาว (ต่างจากวิทยุที่ไม่มีค่าใช้จ่ายส่งข้อมูล)

**สรุปเปรียบเทียบของบทความ**: ระบบโทรมาตร (วิทยุ) มีข้อจำกัดเรื่องพื้นที่ติดตั้ง ค่าใช้จ่ายสูง
และปัญหาสัญญาณวิทยุถูกลดทอนจากสิ่งกีดขวาง (ตึกสูง กทม.) และสภาพอากาศ (ฝนตก) — เป็นข้อได้เปรียบของระบบ
ตรวจวัดระดับน้ำในคลองหลัก (GPRS หลาย Cell Site) ในแง่ความต่อเนื่อง แต่ระบบ GPRS มีค่าบริการรายเดือน
ทำให้ต้นทุนระยะยาวสูงกว่า

## (e) สิ่งที่อธิบายข้อสังเกตของเราวันนี้ (INSTINCT — เชื่อมโยงเข้ากับ FloodConnect 26–27 กันยายน 2026)

**คำเตือนสำคัญ**: บทความนี้เขียนปี 2012 ระบบจริงของ กทม./สนน. ปี 2026 ที่ FloodConnect อ่านค่าอยู่
(ผ่าน thaiwater.net/HII API) **อาจไม่ใช่สถาปัตยกรรมเดียวกัน** ทั้งหมดต่อไปนี้คือการตีความเชื่อมโยง
(INSTINCT) ไม่ใช่การยืนยันว่าระบบปัจจุบันทำงานแบบเดียวกับปี 2012

1. **สถานีแสดงระดับน้ำ = 0.00 เมื่อสถานี "ขัดข้อง"** — INSTINCT: บทความระบุชัดว่าระบบโทรมาตร (วิทยุ UHF)
   "ไม่สามารถส่งข้อมูลได้หากสัญญาณวิทยุขัดข้อง" (หน้า 178) และสัญญาณ "ถูกลดทอนได้ง่ายจากสภาพภูมิประเทศ
   หรือสภาพอากาศ" — หากสถาปัตยกรรมปัจจุบันยังมีองค์ประกอบโทรมาตรไร้สาย ค่า 0.00 ที่ FloodConnect เห็น
   อาจเป็นค่า default/ค่าค้างเมื่อ polling ไม่สำเร็จ ไม่ใช่ระดับน้ำจริงที่ 0
2. **สถานีนิ่งค้างมาหลายปี (stale)** — INSTINCT: ทั้งสองระบบใน 2012 ใช้ polling รอบตายตัว (15 นาที
   ทั้งคู่) ผ่าน RTU/Controller ที่ประมวลผลเฉพาะจุด — หากอุปกรณ์ภาคสนามเสีย (RTU/Modem/เครื่องวัดลูกลอย
   ชำรุด) แต่สถานียังอยู่ใน master list ของ SCADA Server ค่าอาจถูก "ค้าง" ที่ค่าสุดท้ายที่วัดได้จริง
   แทนที่จะถูกลบออกจากรายการ — ตรงกับอาการสถานี stale ที่สังเกตได้
3. **ค่ากระโดด/ผิดปกติทันที (sensor jump)** — INSTINCT: เครื่องวัดแบบลูกลอย (float type) เป็นอุปกรณ์กลไก —
   บทความระบุ pulley 1 รอบ = 50 ซม. หากสายสลิงติดขัด/ลูกลอยเกยสิ่งกีดขวาง (ขยะในคลองเป็นเรื่องจริงในคลอง
   กทม.) อาจทำให้ค่ากระโดดเป็นขั้น ๆ (multiple ของ 50 ซม.) แทนที่จะเปลี่ยนต่อเนื่อง — ยังไม่ได้ตรวจสอบว่า
   ข้อมูลจริงที่เห็นเข้าเงื่อนไขนี้หรือไม่ (OPEN สำหรับการยืนยัน)
4. **สถานะประตูน้ำ (gate) ไม่อยู่ใน public feed** — INSTINCT: บทความระบุว่า "ระดับการเปิด-ปิดประตูระบายน้ำ"
   เป็นหนึ่งใน sensor input ของทั้งสองระบบ (ภายใน SCADA ของศูนย์ควบคุมฯ) — แต่นี่คือข้อมูล**ภายใน**
   ระบบปฏิบัติการของ สนน. เท่านั้น ไม่มีหลักฐานในบทความว่าเผยแพร่สถานะประตูนี้ออกสู่สาธารณะ — สอดคล้องกับ
   ที่ FloodConnect ไม่พบฟิลด์ gate state ใน public feed ของ thaiwater.net
5. **pump_capacity เป็น null** — INSTINCT: บทความระบุว่า "สถานะเครื่องสูบน้ำ" (ทำงาน/ไม่ทำงาน, on-off)
   เป็นข้อมูล digital input เท่านั้น ("On-Off หรือ 1-0") ไม่ใช่ค่าความจุ/อัตราการสูบเป็นตัวเลข (m³/s) —
   หากสถาปัตยกรรมเดิมนี้ยังคงอยู่ ระบบอาจไม่เคยเก็บ "ความจุ" เป็นตัวเลขต่อเนื่องเลยตั้งแต่ต้น
   (มีแต่สถานะ on/off) ซึ่งอธิบายได้ว่าทำไม pump_capacity จึงว่างเปล่าใน feed สาธารณะ
