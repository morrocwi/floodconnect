ปริมาณน้ำฝนในพื้นที่ได้ล่วงหน้า 7 วันขึ้นไปก็ดีนะ" -- ต่อมา (relayed): "ฝนจะมาใน 7 วัน ถ้าให้ดี
ต่อไปด้วยว่ามาเท่าไหร่ ถ้าใช้ API เดียวไม่ได้ก็มาสอง API" -- คือต้องมี**ปริมาณเป็นตัวเลข มม./วัน**
ไม่ใช่แค่ "ฝนจะมา/ไม่มา" และต้องมี**อย่างน้อยสองแหล่งอิสระ**เพื่อเทียบกัน (ตรงกัน = เพิ่มความเชื่อมั่น,
ไม่ตรงกัน = แถว contradiction ตามกติกาเดิมของ repo) -- ต่อมาอีก (verbatim, relayed): **"ตอบเป็น
ช่วงไปเลยก็ได้"** -- คือ**ห้ามฟันธงเป็นตัวเลขเดียวเด็ดขาด** ทุก readout ต้องเป็น **"min-max
(มัธยฐาน ~x) จาก N โมเดล"** พร้อมธง "โมเดลไม่ตรงกัน" เมื่อกระจายมาก (กติกาที่ใช้ในไฟล์นี้:
`max - min > 20 มม.` หรือ `max > 3 x min` (เมื่อ min > 0) -> ถือว่าไม่ตรงกัน) และโชว์ช่วง
ensemble p10-p90 คู่กันเสมอเป็นช่วงที่สอง -- นี่คือ schema ที่ layer-0 IN term ต้องใช้ (§5), ไม่ใช่
แค่ตัวเลือกสำหรับเอกสารนี้เท่านั้น

Epistemic tag ทุกตัวเลขในไฟล์นี้: **VERIFIED** = ดึงเองจริงเห็น payload / **MEASURED** = คำนวณจาก
ข้อมูลที่ดึงเองจริงของ task นี้ / **MEASURED-vs-forecast** = เทียบพยากรณ์เก่ากับค่าประมาณล่าสุดของ
โมเดลเดียวกันเอง (ไม่ใช่เทียบกับสถานีวัดจริง) / **RELAYED** = ได้ยิน/อ่านมา ไม่ได้ดึงเอง /
**OPEN** = ยังไม่ยืนยัน

รายการดิบ+schema เต็มอยู่ที่ `sources/api_census_forecast7d.yaml` -- ไฟล์นี้เป็นสรุปอ่านง่าย
ภาษาไทย + ตารางข้ามแหล่ง (cross-source table) ที่ผลิตจริงจาก `tools/harvest/forecast7d_draft.py`
(ตัวเลขในตารางด้านล่าง**ไม่ได้พิมพ์มือ** -- รันสคริปต์แล้ว copy ผลลัพธ์มา, reproduce ได้ด้วย
`python3 -m tools.harvest.forecast7d_draft`)

## 4. Skill-check แรกของระบบนี้ (MEASURED-vs-forecast, ยังไม่ใช่ MEASURED-vs-observed)

ใช้ Open-Meteo Previous-Runs API เทียบ "GFS พยากรณ์ไว้ว่าไง" กับ "GFS ประเมินย้อนหลังล่าสุดของ
มันเองว่าฝนตกไปเท่าไหร่" (โมเดลเดียวกัน เทียบกับตัวเอง -- **ไม่ใช่**เทียบกับสถานีวัดฝนจริง):

| วันที่ | current-best-estimate (มม.) | พยากรณ์ไว้ล่วงหน้า 1 วัน | พยากรณ์ไว้ล่วงหน้า 3 วัน |
|---|---|---|---|
| 2026-09-22 | 19.4 | 4.2 | 8.8 |
| 2026-09-23 | 31.1 | 24.0 | 14.8 |
| 2026-09-24 | 53.3 | 20.7 | 30.1 |
| 2026-09-25 | 39.4 | 51.1 | 30.7 |
| **2026-09-26** | **117.4** | **27.2** | **11.4** |
| 2026-09-27 | 31.3 | 7.6 | 58.1 |

**พลาดหนักสุด: 26 ก.ย.** -- GFS พยากรณ์ล่วงหน้า 1 วันไว้แค่ 27.2 มม. ล่วงหน้า 3 วันไว้แค่ 11.4 มม.
แต่ค่าประเมินย้อนหลังล่าสุดของตัวมันเองคือ 117.4 มม. -- **underforecast ~4-10 เท่า** สำหรับวันฝน
หนักสุดในสัปดาห์นี้ โดยโมเดลเดียว เทียบกับตัวเอง (tag: `MEASURED-vs-forecast`).

**หมายเหตุสำคัญ (ต้องแยกให้ชัด, อย่าปนกัน):** founder ระบุมา (relayed, ยังไม่ยืนยันในงานนี้) ว่า
เหตุการณ์ฝน 26 ก.ย. มีตัวเลขประมาณ ~203 มม. ที่ไหนสักแห่ง -- ถ้าเป็นค่าจากสถานีวัดฝนจริง (เช่น
thaiwater_rain_24h ที่ต่อไว้ในระบบนี้แล้ว) ของจุด/ช่วงเวลาเดียวกัน จะทำให้ GFS พลาดหนักกว่าที่วัด
ได้ในงานนี้อีก (117.4 เป็นค่า "ประเมินย้อนหลังของโมเดลเอง" ไม่ใช่ค่าสถานีวัดจริง) -- **ยังไม่ยืนยัน
ในงานนี้ว่าตัวเลข 203 มม. มาจากแหล่งไหน สถานีไหน ช่วงเวลาไหนเป๊ะๆ** จึงคง tag `OPEN` ไว้จน
กว่าจะรัน cross-check กับ `thaiwater_rain_24h` (สถานีวัดฝนจริงที่ต่อในระบบนี้อยู่แล้ว) ที่จุด/วันที่
เดียวกันจริง ๆ

**นัยต่อ PROP-FLOOD-06:** โมเดลพยากรณ์ (แม้จะเป็น ensemble หลายสมาชิก/หลายโมเดล) มี MEASURED
ประวัติ under-forecast วันฝนหนักได้มาก -- promoter จากพยากรณ์ล่วงหน้าควรถือเป็น "สัญญาณเตือนล่วงหน้า
แบบมีขอบเขตความผิดพลาดจริง" ไม่ใช่ค่าที่แม่นระดับ commit ตัวเลข -- และควรทวนกับ skill-check นี้
ต่อเนื่องทุกครั้งที่มีเหตุการณ์ฝนหนัก ไม่ใช่ครั้งเดียวจบ.

## 5. คำแนะนำ: อะไรควรต่อเข้าระบบตอนนี้

**ควรต่อ (ผ่าน maker-checker review + `sources/registry.yaml` + fixture/test ก่อน ตาม AGENTS.md §5):**

1. `openmeteo_forecast16d_multimodel` -- ระบุ `model=` ชัดเจนแทน `best_match` เดิม (collect.py
   ปัจจุบันไม่ระบุ model เลย, MEASURED จากการอ่าน parsers.py). ให้ 9 โมเดล deterministic จริง
   (ไม่ใช่ 1 โมเดลลึกลับที่ auto-select) -- เป็นการยกระดับของจริงจาก endpoint เดี่ยวที่ใช้อยู่.
2. `openmeteo_ensemble_daily_precip` -- ให้ 31 สมาชิกจริง (p10/median/p90) แทน/เสริมค่าเดี่ยว.
3. `metno_locationforecast` -- แหล่งอิสระที่สาม ไม่ผูกกับ Open-Meteo เลย (คนละ pipeline,
   คนละ ToS), ต้องใช้ User-Agent เฉพาะของตัวเอง.
4. `openmeteo_previous_runs` (skill_check) -- รันเป็นระยะเพื่อสะสมประวัติความแม่นจริงของแต่ละ
   โมเดล ณ จุดนี้ ก่อนอ้างว่าโมเดลไหน "แม่นกว่า" (ปัจจุบันยังไม่มีตัวเลข skill สะสมพอจะฟันธง).

**ยังไม่ควรต่อตอนนี้ (เหตุผลติดไว้):**

- `windy_point_forecast_api`, `meteoblue_api`, `openweathermap_onecall`, `tomorrow_io_api`,
  `weatherapi_com`, `visualcrossing_timeline` -- ทุกตัวต้อง key (แม้จะฟรีระดับ instant signup
  หลายตัว) ในขณะที่มีแหล่งไม่ต้อง key ครบ 3 แหล่งแล้วซึ่งเกินเกณฑ์ founder ไปแล้ว -- ยังไม่มีเหตุผล
  พอจะเพิ่ม dependency บน 3rd-party key เพิ่ม จนกว่าจะเห็นว่า 3 แหล่งฟรีไม่พอ.
- `weatherapi_com` โดยเฉพาะ -- ถ้าข้อมูล horizon ฟรี = 3 วันจริง (RELAYED, ยังไม่ยืนยัน) จะไม่ผ่าน
  เกณฑ์ >=7 วันของ founder เลย ไม่ว่าจะสมัคร key หรือไม่.
- `ecmwf_open_data_direct`, `noaa_gefs_cpc_keyless` -- Open-Meteo re-serve โมเดลเดียวกันเป็น
  JSON พร้อมใช้อยู่แล้ว, ไปดึง GRIB ดิบเองไม่คุ้มความซับซ้อน.
- `rainviewer_radar_nowcast` -- ใช้ได้สำหรับ "ฝนกำลังตกที่ไหนตอนนี้/ใน 1 ชม.ข้างหน้า" (เสริม
  layer-0 ระยะสั้นมาก) แต่**ไม่ใช่**การตอบโจทย์ 7 วันของ founder -- ยังต้องตรวจ Thailand ground-
  radar coverage จริง (ตอนนี้ OPEN) ก่อนจะเชื่อว่าไม่ใช่แค่ IR satellite fallback.
- `openmeteo_seasonal` -- query ที่ลองครั้งนี้ผิดพารามิเตอร์ (ได้ HTTP 200 แต่ไม่มีข้อมูล), ต้องแก้
  query ก่อน แล้วต้องพิสูจน์ thailand_coverage อีกที (ตอนนี้ OPEN), และ horizon/resolution หยาบ
  เกินไปสำหรับ layer-0 รายวันอยู่แล้ว -- priority ต่ำสุดในกลุ่มนี้.

**การเข้า layer 0 (`docs/LAYER0_IN_OUT_CAPACITY.md`):** เสนอ IN term ใหม่ตาม schema บังคับ
(คำสั่ง founder "ตอบเป็นช่วงไปเลยก็ได้") -- string เดียว ต่อวัน ต่อจุด:

    "ฝนที่จะมา (วันที่ D): {min}-{max} มม. (มัธยฐาน ~{median}) จาก {N} โมเดล
     [โมเดลไม่ตรงกัน ถ้า max-min>20 หรือ max>3xmin] (ensemble p10-p90: {p10}-{p90})"

ห้ามลดรูปเหลือแค่ median/ตัวเลขเดียวที่จุดไหนในระบบเลย (ไม่ใช่แค่เอกสารนี้) -- ทุก layer ที่อ่านค่านี้
ต่อ (PROP-FLOOD-06 promoter, public page) ต้องอ่าน field ทั้ง 4 ตัว (`min`,`max`,`median`,`n`) +
ธง `disagree` เป็น struct เดียวกัน ไม่ใช่แยกอ่านแค่บางตัว. tag ทุกครั้งว่า `RELAYED-forecast`
(มาจากโมเดลพยากรณ์ ไม่ใช่การวัดจริง) และ skill ของแต่ละโมเดล ณ จุดนี้ยังเป็น **OPEN** จนกว่า
`openmeteo_previous_runs` จะถูกรันสะสมพอจะให้ตัวเลข Th_coqc/finite_diagnostic ที่แท้จริง (ดู §4).
Reference implementation ของ struct นี้: `cross_source_daily_summary()` +
`format_range_readout()` ใน `tools/harvest/forecast7d_draft.py` (ยังเป็นฉบับร่าง, ยังไม่ได้ wire
เข้า `site/build_data.py` จริง).

## 6. สิ่งที่ห้ามอ้าง

- **ห้าม**อ้างว่าโมเดลไหน "แม่นกว่าสำหรับไทย" จากความจำ -- ไม่มีแหล่งใดในงานนี้ที่ระบุ skill score
  เฉพาะภูมิภาคเอเชียตะวันออกเฉียงใต้/ไทยอย่างเป็นทางการ; skill-check เดียวที่มีตอนนี้ (§4) คือ
  GFS เทียบกับตัวเอง 6 วัน ไม่พอจะสรุปอะไรทั่วไป.
- **ห้าม**อ้างตัวเลข 203 มม. (ที่ founder relay มา) เป็นข้อเท็จจริงที่ยืนยันแล้วในระบบนี้ -- คง tag
  `OPEN` จนกว่าจะเจอแหล่ง/สถานี/ช่วงเวลาที่ตรงกันจริง.
- **ห้าม**อ้างว่า RainViewer มีเรดาร์ภาคพื้นดินจริงในไทย -- ยืนยันได้แค่ว่า endpoint ใช้งานได้
  (HTTP 200) และมี satellite IR ทั่วโลกแน่ ๆ, ส่วนเรดาร์ภาคพื้นดินเฉพาะไทยยังเป็น OPEN.
- **ห้าม**ปฏิบัติต่อ "current-best-estimate" ใน Previous-Runs API ว่าเป็นค่าสถานีวัดฝนจริง --
  มันคือค่าประเมินย้อนหลังของโมเดลเดียวกันเอง ไม่ใช่ ground truth.
- ไฟล์นี้และ `sources/api_census_forecast7d.yaml` เป็น**การสำรวจ + parser ฉบับร่างเท่านั้น** --
  ยังไม่ได้ผ่าน maker-checker review, ยังไม่ได้เพิ่มลง `sources/registry.yaml`, ยังไม่ได้ wire
  เข้า `collect.py` จริง.
