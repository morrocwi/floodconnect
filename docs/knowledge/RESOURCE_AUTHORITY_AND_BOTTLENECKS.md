## (1) ไฟล์นี้คืออะไร + ป้าย (tag) ที่ใช้

ไฟล์นี้มี 2 ชั้นข้อมูลปนกัน ห้ามปนแท็ก:

| tag | ความหมาย |
|---|---|
| **MEASURED-on-graph** | คำนวณจาก `tools/dag/bottlenecks.py` รันจริงกับ `water_system_dag.mmd` — เป็นเลขคณิตบนกราฟ ไม่ใช่ข้อเท็จจริงภายนอกที่ตรวจสอบแล้ว (กราฟเองมีขอบที่ยังเป็น RELAYED-GENERAL/OPEN ปนอยู่ — ดู §6) |
| **INSTINCT** | การตีความของผู้เรียบเรียงไฟล์นี้ว่าเลขที่คำนวณได้ "แปลว่าอะไร" ในโลกจริง — ไม่ใช่ข้อเท็จจริงที่ตรวจแล้ว ทุกย่อหน้าตีความจะระบุ tag นี้กำกับชัดเจน |
| **RELAYED-GENERAL** | ฐานกฎหมาย (ชื่อ พ.ร.บ./เลขปี) — มาจากความรู้ทั่วไปของผู้เขียนกราฟ **ยังไม่ได้ตรวจกับราชกิจจานุเบกษา** เลขมาตราเป็น OPEN ทั้งหมด |
| **OPEN** | ยังไม่รู้ / ไม่มีข้อมูลในกราฟ |

**คำเตือนสำคัญ**: กราฟต้นทาง (`water_system_dag.mmd`) เอง "แท็กเฉพาะเส้น (edge) ไม่แท็ก node" (ดู
`tools/kg/build_kg.py` docstring หัวข้อ known gaps) ดังนั้นตัวเลขในไฟล์นี้ (เช่น "จำนวนผู้สั่งขัดกัน")
นับจากการมีอยู่ของเส้นในกราฟเท่านั้น ไม่ได้แปลว่าเส้นทุกเส้นมีน้ำหนักความน่าเชื่อถือเท่ากัน — เส้นที่ tag
`OPEN` ในกราฟต้นทาง (เช่น จุดประสานงานที่ยังไม่ยืนยัน) ก็ถูกนับรวมในเลข MEASURED-on-graph นี้ด้วย ผู้ใช้
ต้องเปิด `bottlenecks.derived.json` ดู edge tag ประกอบก่อนอ้างเป็นข้อเท็จจริงเชิงนโยบาย

## (2) วิธีคำนวณ (นิยามกฎ, ตรงตามโจทย์ข้อ 7)

รันด้วย `python3 -m tools.dag.bottlenecks` — parse `water_system_dag.mmd` ด้วย regex **เดียวกัน** กับ
`tools/kg/build_kg.py` (import มาใช้ ไม่ copy) เป็น `networkx.MultiDiGraph` (ใช้ MultiDiGraph ไม่ใช่
DiGraph ธรรมดา เพราะโหนดคู่เดียวกันมีเส้นได้มากกว่า 1 ชนิดจริงในกราฟนี้ — DiGraph ธรรมดาจะทับเส้นทิ้ง):

1. **ผู้สั่งขัดกัน (conflicting commanders)** — node ที่มีเส้น `COMMANDS` (mermaid: `CMD`) เข้ามากกว่า
   หรือเท่ากับ 2 เส้น จากคนละต้นทาง → แสดงรายชื่อผู้สั่งทั้งหมด
2. **ช่องว่างเจ้าของทรัพยากร** — node ชนิด `AS_*`/`DT_*` ที่มีเส้น `OWNS` เข้า **0 เส้น** (ไม่มีเจ้าของ)
   หรือ **≥2 เส้น** (มีเจ้าของซ้อน/ไม่ชัดว่าใครรับผิดชอบจริง)
3. **เส้น SHARES ที่ไม่มีเส้นทางชี้ขาด (arbitration path)** — นิยามชัดเจน: เส้น `SHARES` คู่ (u,v) จะถือว่า
   "มีเส้นทางชี้ขาด" ก็ต่อเมื่อมี node w อย่างน้อย 1 ตัว (w ≠ u, v) ที่ COMMANDS-reach ทั้ง u และ v ได้ —
   ไล่ผ่านเฉพาะเส้น `COMMANDS` ย้อนกลับ (ancestor ใน subgraph ที่มีแต่เส้น COMMANDS เท่านั้น) แบบทอด
   ข้ามชั้นได้ (transitive) ไม่ใช่แค่ผู้สั่งตรง 1 ชั้น ถ้า intersection ของ "ผู้สั่ง u ทุกชั้น" กับ "ผู้สั่ง v
   ทุกชั้น" ว่างเปล่า = ไม่มีใครมีอำนาจสั่งทั้งสองฝ่ายพร้อมกัน = ไม่มีกลไกชี้ขาดเมื่อขัดแย้ง → ถูก flag
4. **จุดล้มเดียว (single point of failure)** — หา articulation point ของกราฟ (แปลงเป็น undirected
   ก่อน) แล้วกรองเฉพาะตัวที่ถอดออกแล้ว **ตัดเส้นทางจาก node `DT_*` ใดๆ ไปยัง node `PP_*` ใดๆ ทุกเส้นทาง
   หมด** (ทดสอบด้วย super-source/super-sink เชื่อม DT_* ทั้งหมด → PP_* ทั้งหมด) **หรือ** ตัดเส้นทางจาก
   "แหล่งทุน" (node ที่มีเส้น `FUNDS` ออก) ไปยัง node `AS_*` ที่ label มีคำว่า pump/ปั๊ม/สูบ ทุกเส้นทาง —
   เกณฑ์นี้ตั้งใจให้ "เข้มงวด" (ต้องตัดทุกเส้นทาง ไม่ใช่แค่เส้นทางเดียว) ผลที่ได้จริง = **0 จุด** (ดู §3.4) —
   นี่เป็นข้อค้นพบเชิงบวกที่แท้จริง ไม่ใช่ script พัง (INSTINCT ตีความว่าทำไมในหัวข้อเดียวกัน)
5. **ทรัพยากรต่อ node หน่วยงาน (`AG_*`)** — ดึงเฉพาะจากกราฟ: OWNS/COMMANDS/FUNDS (out-edge) +
   AUTHORIZES เข้า (in-edge จาก `LAW_*`) + SHARES ทั้งสองทิศ

ทุกเลขในตารางด้านล่างมาจาก `docs/knowledge/bottlenecks.derived.json` (สร้างวันที่สร้างไฟล์นี้) — รันซ้ำ
ด้วยคำสั่งข้างบนเพื่อยืนยันตัวเลขปัจจุบันของกราฟ (กราฟอาจถูกขยายต่อในอนาคต ตัวเลขจะเปลี่ยน)

### 3.4 จุดล้มเดียว (single point of failure) — **0 จุด พบ**

ด้วยนิยามที่เข้มงวด (ต้องตัด **ทุก** เส้นทาง DT_* → PP_* หรือ FUNDS-source → pump ไม่ใช่แค่บางเส้นทาง)
สคริปต์หา articulation point ได้ 31 จุดในกราฟทั้งหมด แต่ **ไม่มีจุดใดตัดได้ครบทุกเส้นทาง** — เพราะกราฟมี
"ช่องทางถึงประชาชน" (`CH_*`) หลายช่องที่ต่อตรงจาก node ข้อมูลไปหาประชาชนโดยไม่ผ่านจุดเดียวกัน (เช่น
`CH_FLOODCONNECT`, `CH_MEDIA`, `CH_1555`, `CH_CELLBC` ล้วนต่อตรงถึง `PP_T1`) และมีปั๊ม/แหล่งทุนหลายจุด
(`AG_BUDGET`, `AG_BMA_COUNCIL`, `AG_DIST_COMMDEV`, `AG_OWNERS`, `DC_COMPENSATE` เป็นแหล่งทุน;
`AS_SPS_POND`, `AS_SPS01`, `AS_PKN_PUMP`, `AS_RID_COAST` ฯลฯ เป็นปั๊ม)

**INSTINCT (การตีความ)**: ผลลัพธ์ "0 จุด" ไม่ได้แปลว่าระบบไม่มีจุดเปราะบาง — แปลว่า **นิยาม "ตัดทุก
เส้นทาง" เข้มงวดเกินกว่าจะจับปัญหาจริงที่การ์ดข่าวชี้ไว้ได้** ปัญหาจริง (ตามการ์ดในคลังนี้) ไม่ใช่ "ไม่มี
เส้นทางสำรองเลย" แต่คือ "เส้นทางสำรองแต่ละเส้นช้ากว่าที่ประชาชนต้องการ" — เช่น การ์ด opinion ชี้ว่า
"หน่วยงานด้านภัยพิบัติราว 30 หน่วยทำงานแยกส่วน" ไม่ใช่ขาดช่องทางแต่ขาดการประสาน
(`docs/knowledge/card_opinion_2026-09-27_warning_incentives.md` ข้อ 2) และคลิป NationTV ชี้ว่า
"สามกฎหมายให้อำนาจซ้อนกันในเหตุเดียว" ทำให้ผู้สั่งจริงไม่ชัดแม้มีผู้สั่งหลายคน
(`docs/knowledge/card_news_2026-09_nationtv_three_laws_overlap.md` ข้อ 1) — คอขวดจริงในกรณีนี้คือ
**ข้อ 3.1/3.2/3.3 (ผู้สั่งขัดกัน/เจ้าของซ้อน/ไม่มีผู้ชี้ขาด) ไม่ใช่ข้อ 3.4** งานถัดไปที่ควรทำ (OPEN, ไม่ใช่
ส่วนของงานนี้) คือวัด "จุดที่ตัดเส้นทางส่วนใหญ่แต่ไม่ทั้งหมด" (weighted/partial cut) แทนเกณฑ์ all-or-
nothing นี้

**เกี่ยวกับ 3 กฎหมายซ้อนกัน (ผู้สั่งขัดกันที่ DC_ALERT/DC_EMERG) — INSTINCT**: คลิป NationTV ชี้ว่า

## (5) ตัวอย่างศึกษา (worked example): ปั๊ม ST.SPS.01-04 หมู่บ้านสัมมากร

ไล่ตามกราฟจริง (MEASURED-on-graph, ทุกเส้นอ้างจาก `bottlenecks.derived.json`):

```
AS_SPS_POND / AS_SPS01  (สถานีสูบบึง/คลองบ้านม้า ST.SPS.01-04)
    เจ้าของ (OWNS):  AG_DDS (สนน., tag V/O) + AG_ESTATE (นิติบุคคลหมู่บ้าน, tag O) — ซ้อน/ไม่ชัด (§3.2)
    ผู้สั่งเดินเครื่อง (COMMANDS -> DC_RUN_SPS):  AG_DDS + AG_ESTATE — ผู้สั่งขัดกัน (§3.1)
    ฐานกฎหมาย (AUTHORIZES):
      - AG_DDS: ไม่มีเส้น AUTHORIZES ตรงในกราฟนี้ (เข้าถึงอำนาจผ่าน AG_BMA_GOV ที่ถูก
        LAW_BMA2528 + LAW_DECENTRAL2542 + LAW_DISASTER2550 AUTHORIZES — อ้อมหนึ่งชั้น)
      - AG_ESTATE: LAW_LANDALLOT2543 (พ.ร.บ.การจัดสรรที่ดิน 2543) AUTHORIZES โดยตรง
    ไฟเข้าปั๊ม (POWER):  AS_GRID (เจ้าของ AG_MEA) — เส้น POWER ไปยัง AS_SPS_POND/AS_SPS01 ติด
      tag OPEN ทั้งคู่ (ไม่ยืนยันว่าไฟจริงต่อถึงหรือมีแผนสำรอง) — ตรงกับ SHARES ที่ไม่มีผู้สั่งร่วม
      ระหว่าง AG_MEA กับ AG_ESTATE (§3.3, §4)
    น้ำไหลถึงประชาชน (WATER):  AS_BANMA -> PP_T1 (เส้นตรง, tag RELAYED) — เป็นหนึ่งในไม่กี่
      เส้นทางที่ตัดตรงจากปั๊มถึงกลุ่มผู้รับผลชั้น T1
```

**จุดที่ต้องมีการ "ร่วมมือกันของ node"** (ตอบตรงโจทย์ผู้ก่อตั้งข้อ 2 ของคำถาม): (ก) `AG_DDS` กับ
`AG_ESTATE` ต้องตกลงกันว่าใครสั่งเดินเครื่อง/ซ่อมปั๊มเมื่อขัดกัน — ปัจจุบันไม่มีเส้นทางชี้ขาดในกราฟ; (ข)
`AG_MEA` กับ `AG_ESTATE` ต้องตกลงเรื่องไฟสำรองสถานีสูบ — เช่นเดียวกัน ไม่มีเส้นทางชี้ขาด; (ค) ทั้งสองคู่
ไม่ปรากฏในกราฟว่ามี node กลางใดๆ (เช่น `AG_DIST_SS`) ทำหน้าที่ประสาน แม้ในทางปฏิบัติสำนักงานเขต
สะพานสูงน่าจะมีบทบาทนี้จริง (INSTINCT — ไม่มีเส้นในกราฟรองรับ ถือเป็นช่องว่างของกราฟเอง ไม่ใช่ข้อสรุปว่า
เขตไม่ทำงานนี้จริง)

## (6) รายการ OPEN

- **มาตรากฎหมายทุกฉบับที่กราฟใช้ยังไม่ตรวจกับราชกิจจานุเบกษา** (RELAYED-GENERAL ทั้งหมด — สืบเนื่องจาก
  `POWER_RESOURCE_MAP.md` และ `WATER_SYSTEM_DAG.md`)
- **เส้น AUTHORIZES/CONSTRAINS ในกราฟยังไม่ครบทุก node** — บาง `AG_*` (เช่น `AG_DDS`) ไม่มีเส้น
  AUTHORIZES ตรงเลย ไม่ได้แปลว่าไม่มีฐานกฎหมาย แค่แปลว่ายังไม่ถูกวาดในกราฟนี้ (ดู §5)
- **กฎ "จุดล้มเดียว" แบบ all-or-nothing ไม่พบ 0 จุด** (§3.4) — ยังไม่มีเวอร์ชัน partial-cut/weighted
  ที่อาจจับคอขวดที่อ่อนไหวจริงได้ดีกว่า — งานถัดไป ไม่ใช่ส่วนของ FOUNDER_TASKS ข้อ 7 นี้
- **ไม่มีข้อมูลกำลัง/ซ่อมบำรุงจริงของ ST.SPS.01-04** (สืบเนื่องจาก `AGENTS.md` §8, ยังเปิดอยู่)
- **ผลกระทบเชิงเวลา (time-to-arbitration)**: กราฟตอบได้แค่ "มี/ไม่มีเส้นทางชี้ขาด" ไม่ตอบว่าถ้ามี ใช้เวลา
  นานแค่ไหนจริง (`PROP-FLOOD-02` ที่ยังไม่ implement ตาม `AGENTS.md` §8 น่าจะเกี่ยวข้องในอนาคต)
